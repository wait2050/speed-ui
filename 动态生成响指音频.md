### Phase 3：engine 运行时随机生成 snap 时刻

| 子任务 | 文件                  | 改动                                                                                                                       |
| --- | ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 3.1 | `PlaybackEngine.ts` | 新增 `private generateSnapTimes(fromMs: number): number[]`：扫描 timeline，累加每个非热身阶段 action/rest 时长，按阶段预算分桶 + 抖动，在桶内随机         |
| 3.2 | `PlaybackEngine.ts` | `scheduleSnapsFrom(fromMs)` 改为：调 `generateSnapTimes` → 用返回的毫秒列表排程 source（替换原本扫 timeline snap 项的逻辑）                       |
| 3.3 | `PlaybackEngine.ts` | 新增 `seed?: number` 字段，让 `Math.random` 可改用 seeded RNG，**确保同一份 timeline 同一份 counts 在 seek/resume 时生成的随机时刻可重现**（避免暂停前后位置漂移） |
| 3.4 | `PlaybackEngine.ts` | `start/pause/resume/seek/triggerSubjectiveClimax/triggerReleaseAfterglow` 全部沿用新 `scheduleSnapsFrom`，无需改签名                |

**算法要点**：

```
对每个非热身 phase (core, sprint_*, climax, afterglow):
  - 累加该 phase 内 action+rest 时长 = totalActionMs
  - 预算 N = counts[phase] 次
  - if N == 0 → skip
  - bucket = totalActionMs / (N+1)         // 等距分桶
  - for k in 1..N:
      center = bucket * k                  // 桶中心
      jitter = (random-0.5) * bucket * 0.5 // ±25% 桶宽抖动
      t = phaseStartMs + center + jitter
      absMs = t
  → 收集所有 absMs 排序
```

**验证**：手动跑 20min timeline + 各 phase 2 次，统计每 phase snap 数 = 配置 N

### Phase 5：暂停/恢复/进度跳转同步验证矩阵

| 场景                            | 期望行为                                                 | 验证手段                            |
| ----------------------------- | ---------------------------------------------------- | ------------------------------- |
| 播放中暂停                         | 当前已排 snap source 全部 `stop()`                         | 听感：暂停后无尾音                       |
| 暂停后恢复                         | 从 elapsed 重新 `generateSnapTimes` + 排程                | 听感：恢复后节奏连贯，snap 数 = 配置          |
| 拖动进度条                         | 同样从新位置重新生成+排程                                        | 听感：seek 后 snap 不堆积、不重复          |
| 触发高潮（triggerSubjectiveClimax） | timeline 被截断重排 → 旧 snap 全清 → 按新 timeline 重新生成        | 听感：高潮后 snap 计数从 0 开始按 climax 配置 |
| 触发余韵（triggerReleaseAfterglow） | 同上                                                   | 同上                              |
| 用户中途换音源                       | 旧 source 自动 `stop()` 不用清空（buffer 换了不影响已排 source 的播放） | 听感：换源后新一次 snap 用新音              |
| 用户清空自定义音源                     | `setSnapSource(null)` → 下次 `loadDefaultSnap`         | 听感：恢复 snap.mp3                  |

**关键不变量**：任何时刻 `scheduledSnapSources` 中的 source 数量 ≤ 各 phase 配置的 snap 总数 × 1 次生成窗口

| 风险                                                   | 概率  | 影响  | 缓解                                                                                                    |
| ---------------------------------------------------- | --- | --- | ----------------------------------------------------------------------------------------------------- |
| 每次 resume 重新生成随机时刻导致 snap 位置不稳定（听感跳）                 | 中   | 中   | 用 seeded RNG；或 resume 时复用首次生成的时刻表（持久化到 `this.snapSchedule: number[]`，clearSnapSources 时仅清 source 不清表） |

### Section 四 · Phase 3 算法（更新部分）

```
generateSnapTimes 流程：
  if !this.snapSeed:
    this.snapSeed = Date.now() & 0xffffffff       // 启动时锁定一次
  rng = mulberry32(this.snapSeed)
  对每个非热身 phase 按预算分桶
  jitter = (rng() - 0.5) * bucket * 0.5          // 用 rng 不用 Math.random
  返回排序后的绝对毫秒列表

不变量：
  - 同一 timeline + 同一 counts + 同一 snapSeed → 输出确定
  - pause/resume/seek 不改 snapSeed → 听感稳定
  - 用户点"重新生成节奏"按钮才更新 snapSeed（可选 UI）
```

## 十一、最终落地方案 · 单条拼接音轨 + 单 BufferSource

> 在 Phase 1–6 完成"运行期随机生成 snap 时刻"后，调试中发现一个本质问题：
> **多 BufferSource 预排程方案在 seek 时会暴露"立刻响指"bug**。
> 原因是 `startSec + (t - fromMs)` 这个调度公式在 t 接近 fromMs 时
> 会算出 ctx 过去时间，被 `Math.max(now, ...)` 兜底成"立刻播放"。
>
> 因此最终方案彻底换架构：**把"多个未来时刻"压成"一条未来音频"**。
> 这才真正符合用户最初的需求"拼接就是拼没有声音的阶段和响指声音"。

### 11.1 架构对比

| 维度         | 多 BufferSource 排程（弃用）                | 单条拼接轨（最终方案）                          |
| ---------- | ----------------------------------- | ------------------------------------- |
| 调度对象       | N 个独立 `AudioBufferSourceNode`        | 1 个 `AudioBufferSourceNode` 播整条 buffer  |
| 启动方式       | `src.start(absTime)` × N             | `src.start(0, 0)` × 1                 |
| seek       | 重新算 N 个 future time + N 次 start     | stop + start(0, offsetSec)            |
| 内存         | 不缓存 audio 数据                       | 缓存 5min 的拼接 buffer（~2.6MB）           |
| 听感稳定性      | seek 公式偏差会触发"立刻响指" bug            | Web Audio 物理保证 start(0, offset) 不可能过去 |
| 是否能换源      | 旧 source 继续播旧 buffer（不可控）           | 立即 stop + 用新 buffer 重建                  |
| 是否需要 N 个 source 管理 | `scheduledSnapSources[]` 列表        | 单字段 `snapTrackSource: SourceNode \| null` |

### 11.2 关键流程

#### 11.2.1 启动（`start()`）

```
1. 锁定 snapSeed = Date.now() & 0xffffffff（pause/resume 复用）
2. computeTimelineTotalMs() → 整条 timeline 总毫秒
3. windowSec = min(totalMs/1000, SNAP_TRACK_MAX_SEC=1h)
4. playSnapTrackFrom(0, windowSec)：
   - stopSnapTrack()                    // 停旧
   - buildSnapTrack(0, windowSec)       // 拼新
   - snapTrackSource = createBufferSource()
   - snapTrackSource.start(0, 0)        // 从 buffer 头开始
```

#### 11.2.2 构建拼接轨（`buildSnapTrack(fromMs, windowSec)`）

```
1. createBuffer(1, ceil(windowSec * 22050), 22050)
   - 采样率 22050Hz（snap 是短促点击，够用；省一半内存）
   - 1 通道 mono
   - 初始全 0（=静音底版）
2. generateSnapTimes() → 绝对毫秒列表（按 phase 分桶 + 抖动）
3. 对每个 snap t：
   localSec = (t - fromMs) / 1000
   placeSnapIntoTrack(trackData, snapData, localSec, 22050)
4. return AudioBuffer
```

**`placeSnapIntoTrack` 是已提取的纯函数**（`src/engine/PlaybackEngine.ts` 顶部 export），
方便单测验证边界条件。

#### 11.2.3 seek / pause / resume

```typescript
// seek
seek(targetMs) {
  this.startTime = ctx.currentTime - targetMs / 1000
  this.playSnapTrackFrom(targetMs, computeSnapWindowSec(targetMs))
  // = stop + build + start(0, 0)
}

// pause
pause() {
  this.stopSnapTrack()   // 保留 buffer；恢复时复用
}

// resume
resume() {
  this.playSnapTrackFrom(elapsedBeforePause, computeSnapWindowSec(elapsedBeforePause))
}
```

**关键不变量**：`start(0, offset)` 的 offset ∈ [0, buffer.duration]，
Web Audio 规范保证不会在 ctx 过去时间播放 → **"立刻响指"bug 类被物理消除**。

#### 11.2.4 窗口滚动（5min 自动续接）

```
scheduleLoop() 每 50ms 检查：
  if (trackEndMs - elapsedMs < 60_000) {     // 剩余 < 1min
    playSnapTrackFrom(elapsedMs, computeSnapWindowSec(elapsedMs))
  }

computeSnapWindowSec(fromMs) =
  min(SNAP_TRACK_WINDOW_SEC,            // 默认 5min
      (timelineTotalMs - fromMs) / 1000, // 不超剩余
      SNAP_TRACK_MAX_SEC)                // 不超 1h 上限
```

- 用户拖到接近 window 末尾 → 透明续接到下一窗口
- 暂停后恢复 → 自动按 `elapsedBeforePause` 重算窗口
- 高潮触发后 timeline 变长 → 触发* 路径里调 `playSnapTrackFrom(this.elapsed, ...)`

#### 11.2.5 换源（用户上传 / 恢复默认）

```typescript
setSnapSourceFromArrayBuffer(arrayBuf) {
  this.snapBuffer = await ctx.decodeAudioData(arrayBuf)
  if (this.snapTrackSource) {                    // 正在播放
    this.playSnapTrackFrom(this.elapsed, ...)    // 立即用新源重建
  }
}

setSnapSource(null) {                            // 恢复默认
  this.snapBuffer = await loadDefaultSnap()
  if (this.snapTrackSource) {
    this.playSnapTrackFrom(this.elapsed, ...)
  }
}
```

### 11.3 内存/性能

| 指标          | 多源方案     | 单条拼接轨（5min 窗口）              |
| ----------- | ------- | --------------------------- |
| 内存占用（连续 20min session） | 几乎为 0（不缓存） | 5min × 22050Hz × 4B = 0.4MB |

## 十二、为什么不用 OfflineAudioContext 预渲染整条

考虑过的替代方案：用 `OfflineAudioContext` 一次性把整条 timeline（5min / 20min / 1h）渲染成完整响指 buffer，存为静态文件。

**否决理由**：
1. 内存爆炸：1h × 44100Hz × 2ch × 4B = 1.4GB，浏览器直接 OOM
2. 即使降到 22050Hz mono × 1h = 158MB，仍嫌大
3. 预渲染意味着**每次配置变化都要重新跑 OfflineAudioContext**（数秒级），交互迟滞
4. 单条拼接轨 + 5min 窗口已经能完全满足听感需求

## 十三、为什么不直接用 MediaElement + <audio> 标签

考虑过的替代方案：HTML `<audio>` 标签播放 snap.mp3，每次响指调 `audio.currentTime=offset; audio.play()`。

**否决理由**：
1. HTMLAudioElement 不能跟 AudioContext 时钟精准同步（会有 50–200ms 漂移）
2. 不能精确控制音量渐变
3. 不能跟节拍器/语音/心跳等共享同一个 mix bus
4. iOS 后台策略对 `<audio>` 标签不友好

Web Audio API + AudioBuffer 是唯一同时满足"精准时钟 + 共享 mix + 后台保活"的选择。
